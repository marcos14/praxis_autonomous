1 Onde o binário fica e com quem ele conversa

Um único serviço instalado na máquina do dev (ou num servidor da equipe). Ele fica fora das pastas dos projetos — os projetos são apenas repositórios git que ele conhece pelo cadastro. Nenhum arquivo do Praxis dentro dos projetos.

Navegador (você / equipe)

Home · Kanban · chat de demanda · perguntas · aprovações · configurações. Toda a gestão é aqui.
http://localhost:7799

Recebe os alertas: perguntas prontas, plano p/ aprovar, concluída, falha, conflito, franquia.
webhooks (saída)

SERVIÇO PRAXIS — %LOCALAPPDATA%\praxis (PRAXIS_HOME)

praxis.exe serve — serviço do Windows, sobe no boot
praxis.db — SQLite: projetos, motores, demandas, chat, perguntas, planos, fases, custos, eventos, logs

worktrees\erp\d51-auditoria\ — demanda 51, em paralelo, isolada
Dentro do serviço: scheduler (limites de paralelismo) + worker pool. Cada execução dispara os harnesses como processos filhos:

2 O fluxo de uma demanda — quem faz o quê

Linhas = atores. O Praxis conduz tudo em background; o usuário só entra nos passos amarelos (③ responder, ⑤ aprovar, ⑨ abrir o MR) — e é avisado por alerta em cada um deles.

3 Branches — duas demandas em paralelo no mesmo projeto

Cada demanda nasce da main e vive numa branch exclusiva dentro do seu próprio worktree. Commits (●) são por fase, com push automático. O retorno para a main é sempre via Merge Request do dev.

Resumo em uma frase: o binário vira um serviço único em %LOCALAPPDATA%\praxis, com banco e worktrees próprios; os projetos cadastrados são só repositórios git de onde ele deriva uma branch exclusiva por demanda (com push automático a cada fase); o usuário gerencia tudo pelo navegador, é acionado por alertas nos três momentos que exigem humano — responder perguntas, aprovar o plano e abrir o Merge Request — e a main só muda pelo MR revisado pelo time.
